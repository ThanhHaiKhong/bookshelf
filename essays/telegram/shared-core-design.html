Thiết kế kiến trúc · lõi chung iOS + Android

Một lõi, hai mặt

Thiết kế lõi nghiệp vụ dùng chung theo đúng mô hình Telegram — nhưng bằng công cụ 2026. Trang này nói về hình dạng API, ranh giới, và những chỗ sẽ cắn bạn; không nói về lịch trình hay thủ tục.

Rust core UniFFI bindings send / subscribe SwiftUI + Compose

01 Đính chính nền tảng

TDLib không phải WASM

Trước khi thiết kế, cần đặt đúng kỳ vọng. Telegram không chạy lõi trong máy ảo hay tải mã lúc runtime. TDLib là thư viện C++ biên dịch native, cho ra hai artifact khác nhau từ cùng một source: static library nhúng vào app iOS, và .so gọi qua JNI trên Android.

Vậy “cách tiếp cận Telegram” chuẩn xác là: một lõi native chung, kèm binding cho từng ngôn ngữ UI. Không phải wasm, không phải interpreter, không phải hot-swap. Điều này quan trọng vì nó loại bỏ cả một lớp phức tạp — không cần runtime trung gian, không cần cơ chế suspend/resume nhân tạo, không đụng chính sách store về tải mã.

Hệ quả thiết kế: lõi được nạp như code thường của app. Gọi vào nó là lời gọi hàm trực tiếp, tốc độ native. Đổi lại, bạn phải build cho từng kiến trúc và ship trong bản phát hành — đúng như mọi thư viện native khác.

02 Công cụ

Rust + UniFFI — TDLib phiên bản 2026

Nếu viết lại TDLib hôm nay, gần như chắc chắn nó sẽ là Rust. Và mảnh ghép làm mô hình này khả thi với đội nhỏ là UniFFI của Mozilla.

Điểm ăn tiền: UniFFI tự sinh binding cho cả Swift lẫn Kotlin từ một định nghĩa duy nhất. Telegram phải viết tay toàn bộ lớp cầu nối này cho từng nền tảng — bạn thì không. Mozilla dùng UniFFI trong Firefox mobile nhiều năm, nên đây không phải công nghệ thử nghiệm.

Ba lý do khác khớp riêng với hoàn cảnh của bạn: native speed đúng ưu tiên chất lượng bạn đặt ra; đội đã viết Rust rồi (lõi hiện tại là Rust) nên không phải tuyển kỹ năng mới; và bạn đã quen mô hình “lõi ra lệnh, host tuân theo” — đây chỉ là bỏ tầng trung gian đi, giữ nguyên triết lý.

04 ABI

Hai cửa, sao chép hình dạng TDLib

Toàn bộ giá trị của mô hình nằm ở chỗ ranh giới phải hẹp. TDLib có td_send đi vào và td_receive đi ra. Bạn cũng chỉ cần hai cửa.

core/src/lib.rsrust
// ── Cửa 1: lệnh đi vào (tương ứng td_send) ─────────────────
impl Core {
    /// Fire-and-forget. Gọi từ thread bất kỳ, không trả kết quả.
    pub fn send(&self, cmd: Command);

    // ── Cửa 2: sự kiện đi ra (tương ứng td_receive) ────────
    pub fn subscribe(&self, listener: Arc<dyn EventListener>)
        -> Arc<Subscription>;
}

// Trait do Swift/Kotlin hiện thực — Rust đẩy event vào đây
pub trait EventListener: Send + Sync {
    fn on_event(&self, event: Event);
}

impl Subscription {
    pub fn cancel(&self);   // hủy tường minh — bắt buộc, xem mục 08
}

// Command mang correlation id, đúng vai trò "@extra" của TDLib
pub struct Command { pub id: String, pub payload: Payload }
pub struct Event   { pub id: Option<String>, pub kind: EventKind }
//                     ↑ Some(id) = trả lời một lệnh; None = server đẩy
Vì sao không phải events() -> Stream? Đây là chỗ dễ thiết kế sai nhất. UniFFI không sinh được Stream/Flow/AsyncSequence — nó chỉ hỗ trợ Future một-lần (async fn → suspend fun / async). Mẫu đúng là đẩy event qua một trait do foreign hiện thực, rồi mỗi bên tự bọc thành idiom của mình — xem mục kế tiếp.

Điểm cần giữ kỷ luật: đừng thêm cửa thứ ba. Mỗi khi ai đó muốn “chỉ thêm một hàm tiện lợi”, ranh giới rộng ra một chút, và giá trị của mô hình mất đi một chút. TDLib giữ được hai cửa suốt nhiều năm — đó không phải ngẫu nhiên.

05 Hai idiom

Cùng một lõi, mỗi bên viết theo cách của mình

Bạn viết một adapter mỏng cho mỗi nền tảng — chỉ một lần, dùng cho mọi domain. Sau lớp đó, đội iOS viết TCA như bình thường và đội Android viết Flow như bình thường. Không ai phải học idiom của bên kia.

iOS — AsyncStream
Android — callbackFlow
Core+Stream.swiftswift
// Adapter — viết một lần
extension Core {
  func events() -> AsyncStream<Event> {
    AsyncStream { cont in
      let sub = subscribe(
        listener: Sink { cont.yield($0) }
      )
      cont.onTermination = { _ in
        sub.cancel()
      }
    }
  }
}

// Dùng trong TCA — y hệt mọi Effect khác
case .onAppear:
  return .run { send in
    for await ev in core.events() {
      await send(.received(ev))
    }
  }
CoreFlow.ktkotlin
// Adapter — viết một lần
fun Core.events(): Flow<Event> =
  callbackFlow {
    val sub = subscribe(
      object : EventListener {
        override fun onEvent(e: Event) {
          trySend(e)
        }
      }
    )
    awaitClose { sub.cancel() }
  }

// Dùng trong ViewModel — Flow bình thường
viewModelScope.launch {
  core.events().collect { ev ->
    reduce(ev)
  }
}
Để ý sự đối xứng: cả hai adapter đều làm đúng ba việc — đăng ký listener, bơm event ra, và gọi cancel() khi consumer dừng. Việc thứ ba là bắt buộc vì UniFFI không tự hủy giúp bạn.

06 Đảo chiều phụ thuộc

Host capabilities — lõi ra lệnh, native tuân theo

Lõi cần làm việc với thế giới bên ngoài: gọi mạng, lưu file, xem giờ, mua hàng. Nhưng nó không được biết URLSession hay OkHttp là gì. Giải pháp: lõi định nghĩa cái nó cần, native cung cấp.

core/src/host.rsrust
// Lõi định nghĩa cổng. Native cắm vào. Mọi tham số truyền by value.
pub trait Host: Send + Sync {
    fn http(&self, req: HttpRequest) -> HttpResponse;
    fn store_read(&self, key: String) -> Option<Vec<u8>>;
    fn store_write(&self, key: String, val: Vec<u8>);
    fn now_ms(&self) -> u64;
}

// Cổng thanh toán — cùng một trait, hai hiện thực
pub trait Billing: Send + Sync {
    fn purchase(&self, sku: String) -> PurchaseResult;
    fn entitlements(&self) -> Vec<String>;
}
// iOS → StoreKit.  Android → Play Billing.  Lõi không biết, không cần biết.

Đây chính là chỗ StoreKit/Play Billing, AdMob, Firebase, và mọi SDK nền tảng cắm vào — qua cổng do lõi định nghĩa, không phải bằng cách lõi gọi thẳng SDK. Nhờ vậy logic “khi nào hiện paywall”, “gate ra sao” nằm trong lõi, còn “mua hàng bằng API nào” nằm ở native.

Ba lưu ý kỹ thuật khi hiện thực trait phía native: tham số không nhận reference, phải truyền by value. Phía Swift, protocol UniFFI sinh ra yêu cầu Sendable nên implementation của bạn phải conform. Phía Kotlin, nếu Rust spawn thread gọi ngược vào JVM, nhớ AttachCurrentThread — không thì mỗi lời gọi phải attach/detach, rất tốn.

07 Ranh giới

Cái gì vào lõi, cái gì ở lại

Đây là quyết định bạn sẽ phải đưa ra hàng chục lần. Có một quy tắc phân loại gọn:

Quy tắc một câu: thứ trả lời câu hỏi “nên làm gì” → vào lõi. Thứ trả lời “vẽ / chụp / phát thế nào” → ở lại native.

08 Thực tế

Những chỗ UniFFI sẽ cắn bạn

UniFFI rất tốt nhưng chưa 1.0, và có vài giới hạn ảnh hưởng trực tiếp đến thiết kế. Biết trước thì né được; biết muộn thì phải sửa API.

Giới hạn và cách xử lý

Một quan sát: gần như mọi giới hạn trên đều nhẹ đi nếu bề mặt FFI của bạn hẹp và đơn giản. Đó là thêm một lý do nữa để giữ đúng hai cửa.

09 Cách triển khai

Tăng dần — và bước 2 là bước quyết định

  1. Một domain trước: chatbot Lõi chỉ chứa chat + auth + gating. Mục tiêu duy nhất: chứng minh vòng send → subscribe chạy trên cả hai nền tảng với adapter thật.
  2. Bọc lại iOS bằng chính lõi đó Đây là bước hay bị bỏ qua nhất và quan trọng nhất. iOS phải dùng chính lõi mới cho domain đó, không phải giữ code Swift cũ song song. Nếu bỏ qua, bạn có hai nguồn sự thật và chúng sẽ lệch nhau — đúng cái bẫy khiến Dropbox phải từ bỏ chiến lược shared code.
  3. Kéo domain thứ hai vào lõi Live score hoặc assistant. Tái dùng toàn bộ hạ tầng binding và adapter đã dựng — chi phí giảm mạnh so với domain đầu.
  4. Chỉ khi đó mới đụng home decor / photo editor Đây là các domain bị chia đôi giữa lõi và native. Làm sau cùng, khi ranh giới đã được kiểm chứng qua hai domain đơn giản hơn.
Vì sao bước 2 quyết định: lõi chung chỉ có giá trị khi nó là nguồn sự thật duy nhất. Một lõi mà chỉ Android dùng thì không phải lõi chung — nó là codebase thứ hai, và bạn vừa tăng gấp đôi chi phí bảo trì thay vì giảm.
