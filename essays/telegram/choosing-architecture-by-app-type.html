Kiến trúc · chọn theo đặc điểm app

Chat app chỉ là một điểm trên bản đồ

Kiến trúc “lõi chung + một chiều + inject dependency” không phải khuôn áp cho mọi app — cũng không phải app nào cũng cần nguyên bộ. Điều đáng học là tách cái luôn đúng khỏi cái tùy app, rồi đọc đặc điểm để chọn.

01 Luận điểm

Không có “một kiến trúc đúng”

Sai lầm thường gặp khi mới học: thấy Telegram làm “lõi C++ chung + UI native” rồi tưởng đó là chuẩn vàng cho mọi app. Thực tế, mỗi kiến trúc là một đánh đổi chỉ hợp lý với một số đặc điểm nhất định.

Cách tư duy đúng là chia kiến trúc thành hai tầng: hằng số — những nguyên tắc đúng với gần như mọi app có giao diện; và biến số — những lựa chọn thay đổi theo bản chất của app. Học được cách phân biệt hai tầng này, bạn tự thiết kế được kiến trúc cho bất kỳ app nào, không cần copy khuôn của ai.

02 Hằng số

Ba thứ đúng với gần như mọi app

Dù là chat, ngân hàng, hay bán hàng — ba nguyên tắc này đều đáng giữ, vì chúng nói về cách tổ chức code, không phải về loại app.

Luồng một chiều
Unidirectional data flow

UI gửi ý định → tầng logic xử lý → state đổi → UI vẽ lại. Không nơi nào tự ý sửa state. Dễ suy luận, dễ tìm bug.

Tiêm phụ thuộc
Dependency injection

Tầng trên khai báo thứ nó cần, được tiêm vào — không tự tạo. Thay thật ↔ giả mà không sửa logic → test được.

Tách bạch
Logic ≠ giao diện

Mọi quyết định nằm ngoài View. View là hàm thuần của state. Đúng cho TDLib, TCA, Redux, Elm... như nhau.

Nói cách khác: ba thứ trên là “miễn phí lợi ích” — hầu như không có app nào thiệt vì áp dụng chúng. Phần còn lại của trang nói về những lựa chọn không miễn phí.

03 Biến số · khung quyết định

Năm trục để đọc một app

Đây là phần cốt lõi. Với mỗi app, hãy tự trả lời năm câu hỏi dưới đây. Mỗi trục là một dải, không phải công tắc bật/tắt — app của bạn nằm đâu đó ở giữa, và vị trí đó kéo kiến trúc về một phía.

Trục 1Realtime hay Request/Response?

Dữ liệu có tự thay đổi khi bạn không làm gì, và cần hiện ngay không?

Request / ResponseHỏi mới có. Chỉ cần async request một lần. VD: catalog, form, tra cứu.
RealtimeServer tự đẩy. Cần luồng update / stream / subscription liên tục. VD: chat, trading, cộng tác.
Trục 2Bao nhiêu logic chung × mấy nền tảng?

Logic nghiệp vụ có phức tạp và phải chạy giống nhau trên nhiều nền tảng không?

Ít logic · 1–2 nền tảngMột codebase native (hoặc cross-platform UI) là đủ. Tách lõi riêng chỉ tổ phí.
Nhiều logic · đa nền tảngĐáng tách lõi chung (C++/Rust/KMP), UI native mỗi nơi. VD: Telegram, Spotify.
Trục 3Có nặng tính toán / hiệu năng tới hạn?

Có xử lý nặng mà ngôn ngữ UI làm không nổi hoặc quá tốn pin?

Nhẹ (CRUD, hiển thị)Không cần native core. Swift/Kotlin thừa sức.
Nặng (codec, routing, ML)Cần lõi native C++/Rust. VD: định tuyến bản đồ, giải mã video, game engine.
Trục 4Offline-first hay Online?

App phải dùng được khi mất mạng, và đồng bộ lại sau đó?

OnlineServer là nguồn sự thật. Gọi API trực tiếp, cache nhẹ.
Offline-first / local-firstLocal DB là nguồn sự thật; ghi local trước, sync engine đồng bộ, xung đột giải bằng CRDT. VD: Notion, Obsidian.
Trục 5Mức nghiêm ngặt về đúng-đắn?

Một lỗi logic gây hậu quả nghiêm trọng tới đâu (tiền, sức khỏe)?

Thấp (giải trí, nội dung)Linh hoạt, ưu tiên tốc độ ra tính năng.
Cao (fintech, y tế)Logic thuần tách rõ, test phủ nặng, DI mạnh để mô phỏng mọi tình huống.
Mẹo đọc: càng nhiều trục nghiêng về phải, app càng “đáng” đầu tư kiến trúc nặng (lõi chung + realtime + local-first). Càng nghiêng về trái, càng nên giữ đơn giản.

04 Áp khung vào thực tế

Bảy loại app dưới cùng một khung

Áp năm trục vào các loại app quen thuộc. Để ý: chỉ một số app đáng tách lõi native — phần lớn thì không.

Nhận ra chưa? Cột “Tách lõi native” đa số là Không. Realtime + lõi C++ chung là kiến trúc đắt, chỉ những app đủ phức tạp và đa nền tảng mới hoàn vốn. Game là ngoại lệ — nó không dùng one-way UI mà dùng game loop, nhắc ta rằng ngay cả “hằng số” cũng có ngoại lệ theo miền.

05 Cạm bẫy

Khi “lõi chung” phản tác dụng — bài học Dropbox

Đây là câu chuyện thật, đáng nhớ hơn mọi lời khuyên. Năm 2013, Dropbox chọn chiến lược chia sẻ code mobile bằng C++ (viết một lần thay vì hai) — thậm chí họ tạo ra công cụ Djinni để nối C++ với Objective-C/Java.

Năm 2019, họ từ bỏ hoàn toàn, quay về code native (Swift/Kotlin) trên từng nền tảng. Bài blog “The (not so) hidden cost of sharing code between iOS and Android” liệt kê cái giá ẩn:

Vì sao thất bại: phải tự xây cả một hệ sinh thái công cụ riêng (Djinni, threading, JSON, con trỏ non-null...); môi trường build tùy biến phức tạp; khác biệt giữa hai nền tảng vẫn phải xử lý riêng; và khó tuyển/giữ dev C++ giỏi. Tổng chi phí lớn hơn lợi ích — mà lợi ích lại nhỏ hơn kỳ vọng.

Bài học không phải “shared core là sai”. Telegram và Spotify vẫn dùng rất thành công. Bài học là: shared core không miễn phí. Nó chỉ hoàn vốn khi lượng logic chung đủ lớn và số nền tảng đủ nhiều (Trục 2 nghiêng hẳn về phải). Với app nhỏ, một nền tảng, logic vừa phải — tách lõi C++ là over-engineering. YAGNI.

06 Áp vào iOS / TCA của bạn

Cùng bộ khung, chỉ đổi “nội dung Effect”

Tin vui: trong iOS/TCA, bạn không phải đổi kiến trúc cho từng loại app. Bạn luôn có State / Action / Reducer / @Dependency (đó là các hằng số ở mục 02). Cái thay đổi theo loại app chỉ là nội dung của Effect — cách dữ liệu quay về reducer.

// Chat — realtime: stream update chảy về liên tục

ChatFeature.swiftswift
case .onAppear:
  return .run { send in
    for await update in telegram.updates() {   // giống td_receive
      await send(.received(update))
    }
  }

// E-commerce — request/response: một lần rồi xong

CatalogFeature.swiftswift
case .onAppear:
  return .run { send in
    let items = try await api.products()      // one-shot
    await send(.loaded(items))
  }

// Note offline — local-first: quan sát DB làm nguồn sự thật

NotesFeature.swiftswift
case .onAppear:
  return .run { send in
    for await notes in database.observeNotes() {  // DB đẩy khi đổi
      await send(.notesChanged(notes))       // sync chạy nền, ghi vào DB
    }
  }
Cùng một hình dạng: cả ba đều là Effect bắn Action về reducer — đúng luồng một chiều. Chỉ khác nguồn: stream mạng / một request / quan sát DB. Chọn kiến trúc = chọn nội dung Effect, không phải đập đi xây lại.

07 Rút ra

Ba câu mang đi

→

Tách hằng số khỏi biến số.One-way data flow + DI + tách logic/UI là nền móng cho mọi app. Realtime, lõi chung, local-first là lựa chọn theo đặc điểm — không mặc định bật.

→

Đọc app trước, chọn pattern sau.Chạy app của bạn qua năm trục. Vị trí trên các trục quyết định kiến trúc, chứ không phải “app nổi tiếng X làm thế nào”.

→

Kiến trúc đắt phải hoàn vốn.Shared core, CRDT, realtime đều có chi phí thật (bài học Dropbox). Chỉ trả khi lợi ích vượt chi phí. Mặc định: giữ đơn giản.
