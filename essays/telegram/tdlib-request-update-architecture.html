Kiến trúc · lõi C++ chung + UI native

Mô hình Request / Update của TDLib

Cách một app native (Swift/iOS) “nói chuyện” với lõi C++ của Telegram: gửi JSON một chiều, nhận JSON chiều ngược lại trên một thread riêng — và vì sao mô hình đó chính là TCA mà bạn đang dùng, chỉ khác lớp áo.

td_send td_receive @extra updateNewMessage ↔ TCA: Action / Effect

01 Bức tranh lớn

TDLib là tầng lõi, không phải tầng giao diện

Telegram không chia sẻ giao diện giữa các nền tảng như Flutter hay React Native. Nó chia sẻ lõi logic: một thư viện C++ tên TDLib (Telegram Database Library) chứa toàn bộ giao thức mạng MTProto, mã hóa, cache tin nhắn và đồng bộ trạng thái.

Mỗi nền tảng — iOS (Swift), Android (Kotlin), Desktop (Qt/C++) — chỉ viết phần UI native riêng, rồi gọi vào cùng một lõi đó. Câu hỏi kiến trúc cốt lõi là: UI và lõi nói chuyện với nhau qua ranh giới nào? Câu trả lời — và là điều đáng học nhất — là ranh giới đó cực kỳ hẹp: chỉ vài hàm C, và dữ liệu đi qua nó luôn là một chiều.

Điểm chốt: UI càng “ngu” càng tốt — nó chỉ vẽ và bắt chạm. Mọi thứ “thông minh” nằm ở lõi. Đây là unidirectional data flow, và nó lặp lại nguyên vẹn trong TCA.

02 Nguyên tắc nền tảng

Bất đồng bộ hoàn toàn, và nhất quán

Docs chính thức mô tả TDLib bằng hai từ khóa quyết định cả kiến trúc:

Fully-asynchronous. Request gửi tới TDLib không chặn nhau và không chặn gì cả; phản hồi được gửi về khi nào nó sẵn sàng. Không có lời gọi mạng nào “đứng đợi” trả về giá trị.

Consistent. TDLib đảm bảo mọi update được giao đúng theo thứ tự chúng phát sinh. Nhờ vậy UI có thể áp dụng update một cách tuần tự mà không sợ dữ liệu lệch.

Vì sao Swift gọi qua “JSON interface” chứ không bind thẳng C++?

TDLib có sẵn interface C++, Java, .NET. Nhưng cách được khuyến nghị cho hầu hết trường hợp là JSON interface — một nhúm hàm C thuần (C ABI). Bất kỳ ngôn ngữ nào gọi được hàm C đều dùng được, và Swift gọi hàm C trực tiếp qua bridging header. Vì thế gần như mọi wrapper Swift (TDLibKit, TDLib-iOS…) đều đi qua JSON interface thay vì bind trực tiếp vào các class C++.

03 Vòng đời một client

Bốn hàm, và một vòng lặp

Toàn bộ bề mặt tiếp xúc giữa Swift và lõi C++ gói gọn trong bốn hàm (API hiện đại):

  1. td_create_client_id() Tạo một client và trả về clientId. Có thể tạo nhiều client trong cùng tiến trình.
  2. td_send(clientId, json) Gửi request dưới dạng chuỗi JSON. Fire-and-forget: hàm trả về ngay, gọi được từ bất kỳ thread nào, không có giá trị phản hồi.
  3. td_receive(timeout) Nhận response và update dưới dạng JSON. Chỉ được gọi từ một thread duy nhất tại một thời điểm — nên đặt nó trong một thread nền chuyên dụng chạy vòng lặp.
  4. td_execute(json) Chạy đồng bộ, trả kết quả ngay — nhưng chỉ hợp lệ với số ít method có ghi “Can be called synchronously” trong docs (ví dụ parse text, set log level).
Mấu chốt: send và receive là hai kênh tách biệt. Bạn không bao giờ nhận kết quả ngay tại chỗ gọi td_send. Bạn đẩy JSON ra một đầu, rồi liên tục hứng JSON ở đầu kia.

04 Sơ đồ luồng dữ liệu

Hai kênh một chiều, không phải một cuộc gọi hai chiều

Đây là mô hình tinh thần cần khắc sâu. Không có “gọi hàm rồi nhận về”. Có hai dòng chảy song song ngược hướng: lệnh đi ra bằng td_send, kết quả và sự kiện quay về bằng td_receive trên một thread riêng.

send · request đi ra receive · response & update quay về

// Lệnh chảy phải sang trái-qua-phải bằng màu xanh; kết quả & sự kiện chảy ngược bằng màu hổ phách.

Một câu để nhớ: Swift không bao giờ nhận giá trị trả về trực tiếp từ một request mạng. Nó đẩy JSON đi một chiều và hứng JSON ở chiều kia trên thread khác.

05 Cơ chế khớp

Vậy response nào là của request nào? — @extra

Nếu mọi thứ bất đồng bộ và kết quả về trên một thread khác, làm sao biết một response là trả lời cho request nào? TDLib dùng một field tương quan (correlation id) đơn giản: bạn gắn @extra vào request; response tương ứng sẽ mang @extra y hệt.

Trong mô hình đa client, mỗi object nhận về còn có @client_id để biết nó thuộc client nào.

request.jsonjson
{
  "@type": "getChat",
  "chat_id": 777000,
  "@extra": "req-42"   // id do bạn tự đặt
}
response.jsonjson
{
  "@type": "chat",
  "id": 777000,
  "title": "Telegram",
  "@extra": "req-42",  // khớp lại đúng request
  "@client_id": 1
}

06 Code thật

Swift ↔ C, ba nhịp

Trong Swift, một request chỉ là dictionary được serialize thành JSON rồi đẩy vào hàm C. Ba nhịp: gửi, vòng lặp nhận, và gọi đồng bộ cho vài method đặc biệt.

TDClient.swiftswift
// 1 · GỬI — fire-and-forget, gọi từ thread bất kỳ
let request: [String: Any] = [
  "@type": "setTdlibParameters",
  "api_id": 287311,
  "device_model": "iPhone",
  "@extra": "init-1"
]
td_send(clientId, jsonString(from: request))

// 2 · NHẬN — một thread nền riêng, lặp mãi
Thread.detachNewThread {
  while isRunning {
    guard let raw = td_receive(10.0) else { continue }
    let object = decode(String(cString: raw))

    if let extra = object["@extra"] as? String {
      resolvePending(extra, with: object)   // → response
    } else {
      handleUpdate(object)                   // → update đẩy
    }
  }
}

// 3 · ĐỒNG BỘ — chỉ cho method "Can be called synchronously"
let res = td_execute(jsonString(from: [
  "@type": "getTextEntities",
  "text": "@user #tag"
]))  // trả kết quả ngay, không qua vòng lặp
Để ý nhịp 2: một điểm rẽ duy nhất quyết định tất cả — có @extra thì đây là câu trả lời cho một lệnh; không có thì đây là sự kiện server tự đẩy về.

07 Hai loại JSON quay về

Response vs Update

Mọi thứ hứng được từ td_receive rơi vào đúng một trong hai loại. Phân biệt được chúng là hiểu được toàn bộ mô hình.

Response
Trả lời cho một request

Do bạn châm ngòi. Bạn gửi một lệnh, đây là kết quả của đúng lệnh đó.

Khớp bằng @extra. Đến đúng một lần cho mỗi request.

Update
Sự kiện server tự đẩy

Không ai hỏi cả. Server chủ động báo trạng thái đổi — tin mới, người đang gõ, kết nối đổi.

Không có @extra. Ví dụ updateNewMessage, updateChatReadInbox. Đến bất cứ lúc nào, nhiều lần.

Đây chính là mấu chốt “app realtime”: UI không phải hỏi liên tục “có tin mới chưa?”. Nó chỉ ngồi hứng update và vẽ lại. Luồng dữ liệu vẫn một chiều: server → lõi → update → UI.

08 Đối chiếu — điều bạn đến để học

TDLib chính là TCA, khoác áo C

Nếu bạn đang viết TCA (The Composable Architecture) mỗi ngày, bạn đã hiểu TDLib rồi — chỉ là chưa nhận ra. Cả hai đều là unidirectional data flow: UI gửi ý định, một tầng logic thuần xử lý, side-effect bất đồng bộ quay kết quả về dưới dạng cùng một loại “ý định”.

Ánh xạ khái niệm
TDLibTCAÝ nghĩa chung
td_send(json) store.send(Action) UI gửi ý định, không tự sửa statemột chiều đi vào lõi/reducer
Lõi C++ xử lý Reducer + Effect Logic thuần + side-effect, tách hẳn khỏi Viewnơi duy nhất được đổi state
td_receive → object Effect .send(Action) Kết quả async quay lại lõi dưới dạng một action mớikhông trả thẳng cho chỗ gọi
@extra correlation effect id · .cancellable(id:) Định danh để khớp / hủy một tác vụ asyncbuộc kết quả về đúng nơi
updateNewMessage long-running Effect (stream) Server đẩy liên tục → sinh action nối tiếp.run { send in for await … }
UI chỉ vẽ View đọc State, gửi Action View “ngu”, không giữ logicrender là hàm thuần của state
Cùng một hình dạng: Action đi vào → tầng logic xử lý → Effect/update bắn action mới về → state đổi → View vẽ lại. Đổi td_send/td_receive thành store.send/Effect là bạn có TCA; đổi ngược lại là bạn có TDLib.

09 Rút ra

Ba bài học mang đi được

→

Ranh giới hẹp là sức mạnh. Toàn bộ giao tiếp UI↔lõi gói trong ~4 hàm và một định dạng JSON. Ranh giới càng nhỏ, hai bên càng thay đổi độc lập — Telegram viết lại UI iOS mà không đụng lõi, và ngược lại.

→

Một chiều thì suy luận được. Vì dữ liệu chỉ chảy một hướng (ý định vào, kết quả/sự kiện ra dưới dạng cùng một loại thông điệp), bạn luôn biết state đổi ở đâu và vì sao. Bug UI không lẫn với bug logic.

→

Lõi thuần thì test được. Lõi C++ (hay Reducer trong TCA) không phụ thuộc màn hình — cho input, kiểm output. Đó là lý do cả TDLib lẫn TCA đặt mọi logic ra khỏi View.

Muốn thực hành ngay? Trong một feature TCA nhỏ của bạn, thử tự nhủ: store.send = td_send, Effect trả action = td_receive, một .run stream = luồng update. Bạn sẽ thấy mình đang viết một “TDLib mini” mỗi ngày.
